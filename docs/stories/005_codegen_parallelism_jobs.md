# Parallel `gentest_codegen` scan slots

> **Status:** Implemented in 1.0.0. Unlike most stories, this note describes the
> current design (gentest 2.0.0), including the two-wave scan that header
> registration added.

This note documents how `gentest_codegen` parallelizes parsing/emission across
predeclared scan slots and how to verify that parallel output remains identical
to serial output. With header registration, each authored source and each header
listed in the target is one scan slot. Named-module mock targets scan generated,
module-specific inputs instead.

## Terminology

- **Invocation**: a single `gentest_codegen ...` process started by the build system.
- **Input scan slots**: target-unique slots for authored sources (`authored-tu`)
  and listed headers (`fallback-header`) with header registration, the sources of
  a `MODULE_REGISTRATION` target, or module-specific generated inputs for
  named-module mock targets.
- **Codegen job**: a **worker thread inside one `gentest_codegen` process**, used to parse/emit multiple scan slots concurrently.

Important: this is independent of `cmake --build -j` / Ninja scheduling, which controls how many *processes / build edges* run in parallel.

## Controls

Parallelism is controlled by:

- `gentest_codegen --jobs=<N>` (0 = auto)
- `GENTEST_CODEGEN_JOBS=<N>` (same semantics; convenient for benchmarks/scripts)
- the CMake cache variable `GENTEST_CODEGEN_JOBS` (default `1`; `0` or `AUTO`
  means auto). CMake passes it as `--jobs` whenever it runs codegen for a target.
  If the environment variable is set at the first configure, it seeds this cache
  value.

Precedence:

- If `--jobs` is passed (including `--jobs=0`), it overrides `GENTEST_CODEGEN_JOBS`.
- If `--jobs` is not passed, `GENTEST_CODEGEN_JOBS` (when set) supplies the default.
- Codegen commands generated by CMake always pass `--jobs`, so the environment
  variable does not affect them at build time. Change the cache variable instead.

Auto mode (`0`) uses `std::thread::hardware_concurrency()` (clamped to the number of scan slots, with a fallback to 1 if the runtime reports 0).

`GENTEST_CODEGEN_JOBS` also accepts `auto` (case-insensitive) as a synonym for `0`.
`gentest_codegen` ignores an invalid value with a warning; CMake rejects one at
configure time.

Two environment variables help when you debug the scan:

- `GENTEST_CODEGEN_FORCE_SERIAL_PARSE=1` parses every slot serially, whatever the
  job count. Emission keeps the job count.
- `GENTEST_CODEGEN_LOG_PARSE_POLICY=1` prints the parse decision of an invocation
  with more than one slot, for example `gentest_codegen: using multi-TU parse jobs=4`.

## When parallelism is used

Parallel parsing/emission is enabled only when:

- per-slot output mode is active (`--tu-out-dir` is used), **and**
- the invocation has **more than one** input scan slot, **and**
- resolved `jobs > 1`.

## High-level flow (one invocation)

```text
Ninja / CMake target build
  |
  +-- runs: gentest_codegen  (1 process)
       slots:  [cases_0.cpp, cases_1.cpp, listed_header.hpp, ...]
       jobs:   K   (from --jobs or GENTEST_CODEGEN_JOBS; 0=auto)

       SCAN PHASE  (parallel when K>1 and slots>1)
         wave 1: authored-tu slots, each with its own compile command
         wave 2: fallback-header slots that no wave-1 slot included
         warm-up: parse the first slot of the first non-empty wave serially
                  (initializes LLVM/Clang singletons)
         per wave: shared atomic "next_index" over the wave's remaining slots
         K worker threads:
            loop:
              idx = next_index++
              if idx >= wave_size: exit
              parse that slot with its own clang-tooling objects
              store ParseResult[slot]

       MERGE PHASE  (single thread)
         concatenate all ParseResult[*] cases/fixtures/mocks
         merge declarations that several slots saw
           (one owner slot each; differing redeclarations are errors)
         enforce cross-slot name uniqueness
         sort cases

       EMIT PHASE (per-slot registration sources, parallel when K>1 and slots>1)
         tasks = indices 0..N-1 for the same slot list
         shared atomic "next_index"
         K worker threads:
            loop:
              idx = next_index++
              if idx >= N: exit
              render + write tu_XXXX_*.header_registration.gentest.cpp
              (a slot that owns nothing gets a valid, empty source)

       MOCK OUTPUTS (single thread)
         render + write target/domain mock registry and implementation headers
```

Scan slots are effectively “pushed to a queue”, implemented as an atomic task index that workers consume from (no explicit `std::queue`).

## Implementation notes (correctness + determinism)

- **Thread isolation during parsing**
  - Each worker creates its own `clang::tooling::ClangTool`, `MatchFinder`, and collectors, and writes only to its per-index `ParseResult`.
  - Results are merged after all workers join.

- **Two scan waves**
  - Authored sources are scanned first, each with its exact compile command.
  - A listed header gets its own scan only when no authored source included it.
    Otherwise its slot keeps an empty result, and its declarations come from the
    authored source's compile command.

- **Warm-up parse to avoid TSAN first-use races**
  - When `jobs > 1`, `gentest_codegen` parses the first slot of the first
    non-empty wave serially before it starts worker threads. Before any parse,
    the main thread also initializes LLVM's statistics registry
    (`prime_llvm_statistics_registry()`).
  - Some system LLVM/Clang builds can report TSAN data races during first-use
    singleton initialization when many translation units (TUs) start parsing
    concurrently.

- **Worker stack size**
  - On Linux, `gentest_codegen` links with `-Wl,-z,stack-size=8388608` to request
    an 8 MiB default thread stack. musl's default is too small for Clang's
    template recursion ([story 012](012_libclang_musl_parallel_parse_crash.md)).
  - The CMake cache variable `GENTEST_CODEGEN_DEFAULT_THREAD_STACK_SIZE` sets the
    size in bytes; `0` keeps the toolchain default.

- **Deterministic output**
  - After merge, cases are sorted by `display_name` before emission.
  - Duplicate names are checked across slots on `base_name` (`suite/name`) and
    then on the final display name, so serial and parallel runs report the same
    duplicates.

- **Mock headers during codegen**
  - During codegen (`-DGENTEST_CODEGEN=1`), `gentest/mock.h` skips including the generated mock registry/impl headers.
  - This prevents re-parsing stale/partial mock outputs while codegen scans multiple authored/fallback slots.

## Verification tooling

### 1) Multi‑TU codegen bench target

The repo defines a **codegen-only** benchmark target that invokes `gentest_codegen` once with many authored scan slots:

- `gentest_codegen_parallel_bench` (custom target)
- backed by: `gentest_codegen_parallel_bench_obj` (object library)

Build it:

```bash
cmake --preset=debug-system --fresh
cmake --build --preset=debug-system --target gentest_codegen_parallel_bench --clean-first -j 16
```

### 2) Equivalence check: serial vs parallel outputs

Use `scripts/verify_codegen_parallel.py` to hash every output declared by the
codegen command—including the generated registration sources, the artifact
manifest, and mock-domain outputs—and compare:

```bash
python3 scripts/verify_codegen_parallel.py \
  --build-dir build/debug-system \
  --target gentest_codegen_parallel_bench_obj \
  --serial-jobs 1 \
  --parallel-jobs 0 \
  --repeats 5
```

### 3) Timing different `GENTEST_CODEGEN_JOBS` caps

`scripts/bench_compile.py` can run the exact codegen command from `build.ninja` with a chosen cap:

```bash
python3 scripts/bench_compile.py \
  --build-dir build/debug-system \
  --no-clean \
  --codegen-only \
  --targets gentest_codegen_parallel_bench_obj \
  --codegen-jobs 4
```

Both scripts set only the `GENTEST_CODEGEN_JOBS` environment variable before
they run the command from `build.ninja`. That command already passes `--jobs`
with the CMake cache value, and `--jobs` wins. On a CMake build tree,
`--serial-jobs`, `--parallel-jobs` and `--codegen-jobs` therefore don't change
the job count: every run uses the cache value.

## Limitations / expectations

- If a given test target has only **one** scan slot, a single `gentest_codegen` invocation won’t benefit from internal parallelism.
  - The speedups show up when a single invocation sees many authored and fallback-header slots.
- Internal codegen job parallelism can interact with build-system parallelism:
  - `cmake --build -j X` can run multiple `gentest_codegen` processes in parallel;
  - each process can itself use up to `--jobs` threads.
  - CMake defaults `GENTEST_CODEGEN_JOBS` to `1` for this reason. Raise it when
    one target has many slots and the build runs few codegen commands at once.
